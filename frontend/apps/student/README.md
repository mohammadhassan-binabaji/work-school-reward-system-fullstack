# سامانه پاداش دانش‌آموزی - پروژه اندروید (Capacitor)

این مستند راهنمای جامع راه‌اندازی، توسعه، همگام‌سازی و تولید خروجی اندروید (APK / AAB) برای اپلیکیشن دانش‌آموز با استفاده از **Capacitor 8** است.

---

## ۱. مشخصات پروژه اندروید

* **محیط فریم‌ورک وب:** Vue 3 + Vite + TypeScript + Pinia + Tailwind CSS
* **نسخه خازن (Capacitor):** `8.5.3` (شامل `@capacitor/core`، `@capacitor/android`، `@capacitor/cli` و افزونه `@capacitor/app@8.1.2`)
* **شناسه برنامه (Application ID / Package Name):** از `VITE_ANDROID_APP_ID` در `frontend/.env` خوانده می‌شود.
  > **نکته بسیار مهم:** شناسه برنامه (`appId`) شناسه یکتا و ثابت اپلیکیشن در پلتفرم اندروید و فروشگاه‌های نرم‌افزاری است. شناسه فعلی را پس از انتشار عمومی تغییر ندهید؛ تغییر آن امکان به‌روزرسانی نسخه‌های قبلی کاربران را از بین می‌برد.
* **نام نمایشی برنامه (App Name):** `نوین من`
* **مسیر پروژه نیتیو اندروید:** `frontend/apps/student/android`
* **پوشه بیلد وب (Web Directory):** `frontend/apps/student/dist`

---

## ۲. پیش‌نیازها و نسخه‌های ابزارها

برای ساخت و اجرای پروژه در اندروید، ابزارهای زیر مورد نیاز است:

1. **Node.js:** نسخه `22` یا بالاتر (در این مخزن نسخه `v24.18.1` و `npm 12.0.2` استفاده شده است).
2. **Java Development Kit (JDK):** نسخه `JDK 17` یا `JDK 21` (نسخه پیشنهادی برای Android Gradle Plugin 8.x و Capacitor 8). متغیر محیطی `JAVA_HOME` باید به درستی تنظیم شده باشد.
3. **Android Studio:** نسخه پایدار (Ladybug، Koala، یا جدیدتر).
4. **Android SDK:**
   * `compileSdkVersion`: **36**
   * `targetSdkVersion`: **36**
   * `minSdkVersion`: **24** (اندروید 7.0 و بالاتر)

---

## ۳. دستورات کاری و اسکریپت‌ها

تمامی دستورات از ریشه مونو‌ریپو یا از داخل پوشه `frontend` با استفاده از npm قابل اجرا هستند:

### ۳.۱. نصب وابستگی‌ها
```bash
# از ریشه مخزن:
npm --prefix frontend install
```

### ۳.۲. اجرای تست‌های یونیت
```bash
# اجرای تست‌های سرویس نسخه و مقایسه معنایی:
npm --prefix frontend run test:student
```

### ۳.۳. بیلد پروداکشن وب و همگام‌سازی با اندروید
```bash
# کامپایل فرانت‌اند دانش‌آموز:
npm --prefix frontend run build:student

# همگام‌سازی است‌های وب و پلاگین‌ها با پروژه اندروید:
npm --prefix frontend run cap:sync:student

# یا اجرای همزمان بیلد و همگام‌سازی:
npm --prefix frontend run cap:build:student
```

### ۳.۴. باز کردن پروژه در Android Studio
```bash
npm --prefix frontend run cap:open:student
```
یا می‌توانید به صورت دستی نرم‌افزار **Android Studio** را باز کرده و پوشه `frontend/apps/student/android` را انتخاب (Open) کنید.

## ۴. پیکربندی شبکه و آدرس API (توسعه در برابر تولید)

کلاینت متمرکز HTTP (`ApiClient`) و سرویس نسخه از متغیرهای محیطی استاندارد Vite استفاده می‌کنند.

### ۴.۱. محیط توسعه محلی (Local Development)
در فایل مشترک `frontend/.env` (که از `frontend/.env.example` ساخته می‌شود):
* **در مرورگر وب سیستم:** درخواست‌ها از مسیر هم‌مبدأ `/api/v1` عبور می‌کنند و Vite آن مسیر را در توسعه به بک‌اند proxy می‌کند.
* **در شبیه‌ساز اندروید (Android Emulator):** آدرس `localhost` در شبیه‌ساز به خود دستگاه مجازی اشاره دارد، نه سیستم میزبان شما. برای اتصال از شبیه‌ساز به سرور بک‌اند در پورت ۳۰۰۰ سیستم میزبان، از آدرس آی‌پی روتر مجازی اندروید استفاده کنید:
  ```env
  VITE_API_BASE_URL=http://10.0.2.2:3000/api/v1
  VITE_STORAGE_BASE_URL=http://10.0.2.2:3000
  VITE_APP_VERSION_URL=http://10.0.2.2:5173/app-version-v2.json
  ```
* **در دستگاه واقعی (Physical Device via Wi-Fi):** از آی‌پی شبکه محلی سیستم (مانند `http://192.168.1.50:3000/api/v1`) استفاده فرمایید.

### ۴.۲. محیط تولید واقعی (Production)
برای بیلد نهایی، مقدارهای API، مبدأ ذخیره‌سازی و فایل نسخه را در همان فایل `frontend/.env` با نشانی‌های واقعی **HTTPS** تنظیم کنید. `VITE_ANDROID_APP_ID` نیز باید شناسه انتشار فعلی باقی بماند.
> **هشدار امنیتی:** پروتکل HTTP بدون رمزنگاری (Cleartext HTTP) در نسخه‌های پروداکشن اندروید به صورت پیش‌فرض توسط سیستم‌عامل مسدود می‌شود. از آدرس‌های `localhost` یا پروتکل‌های ناامن در پروداکشن استفاده نکنید. همچنین کلیدهای محرمانه نباید در متغیرهای فرانت‌اند قرار گیرند، زیرا در خروجی برنامه کامپایل می‌شوند.

### نشست ورود و ذخیره گذرواژه

* در نسخه وب دانش‌آموز، ورود با کوکی HttpOnly و CSRF انجام می‌شود و شناسه نشست در `localStorage` یا `sessionStorage` ذخیره نمی‌شود.
* در اندروید، endpoint مجزای `/auth/mobile-login` نشست را به‌صورت credential برمی‌گرداند. با فعال‌بودن «مرا به خاطر بسپار»، credential نشست با کلید Android Keystore رمزگذاری و در فضای خصوصی برنامه ذخیره می‌شود؛ بدون آن فقط در حافظه فرایند باقی می‌ماند. عمر سمت سرور به‌ترتیب ۳۰ روز و یک ساعت است.
* پس از ورود اندروید، برنامه پیشنهاد اختیاری ذخیره نام کاربری و گذرواژه را از طریق Android Credential Manager نشان می‌دهد. این کار مستقل از گزینه ماندگاری نشست است؛ لغو پیشنهاد، ورود موفق را لغو نمی‌کند.
* در صفحه ورود اندروید، با اولین تمرکز روی فیلد کد ملی یا رمز عبور، برنامه از Android Credential Manager برای پیشنهاد گذرواژه ذخیره‌شده درخواست می‌کند. با انتخاب آن، هر دو فیلد پر می‌شوند و ورود خودکار انجام نمی‌شود. در نبود گذرواژه یا لغو پنجره، ورود دستی بدون پیام در دسترس می‌ماند.
* فرم ورود باید `name="username"` / `autocomplete="username"` و `name="password"` / `autocomplete="current-password"` را حفظ کند تا Autofill سیستم در صورت پشتیبانی کار کند.
* برای اتصال یکپارچه Password Manager بین اپ و وب، فایل Digital Asset Links را فقط پس از تهیه SHA-256 fingerprint واقعی کلید امضای انتشار تنظیم کنید. از fingerprint آزمایشی یا placeholder در نسخه انتشار استفاده نکنید.

## ۵. سیستم مدیریت نسخه و به‌روزرسانی اندروید

نسخه‌های جدید اپلیکیشن اندروید، فایل استاتیک `app-version-v2.json` را از مبدأ تنظیم‌شده در `VITE_APP_VERSION_URL` دریافت می‌کنند. این قابلیت فقط برای اپ بومی اندروید است و به اندپوینت‌های بک‌اند NestJS وابستگی ندارد.

### ۵.۱. حفظ سازگاری نسخه‌های قدیمی

نسخه‌های نصب‌شده قبلی همچنان `app-version.json` را با ساختار قدیمی می‌خوانند. این فایل و ساختار آن را حذف یا به v2 تبدیل نکنید؛ تا زمانی که نسخه‌های قدیمی پشتیبانی می‌شوند، مقدارهای `latestVersion`، `minimumVersion` و `updateUrl` آن را با مقصد سازگار به‌روز نگه دارید. مقدار `updateUrl` قدیمی فعلاً همان `/download/student.apk` است.

بیلد جدید باید `VITE_APP_VERSION_URL` را به آدرس `app-version-v2.json` تنظیم کند. فایل v2 را قبل از انتشار APK/AABی که این ساختار را می‌خواند، روی میزبان قرار دهید. بیلدهای قدیمی مسیر قبلی خود را حفظ می‌کنند و با انتشار فایل جدید، ساختارشان تغییر نمی‌کند.

### ۵.۲. ساختار فایل نسخه v2

فایل نمونه در `frontend/apps/student/public/app-version-v2.json` قرار دارد و همراه بیلد وب در ریشه خروجی کپی می‌شود:

```json
{
  "schemaVersion": 2,
  "platform": "android",
  "minimumVersion": "3.2.0",
  "minimumVersionCode": 8,
  "releases": [
    {
      "version": "3.2.0",
      "versionCode": 8,
      "notes": []
    },
    {
      "version": "3.2.6",
      "versionCode": 10,
      "notes": ["نمونه یادداشت فارسی قابل مشاهده برای کاربر"]
    },
    {
      "version": "4.0.0",
      "versionCode": 11,
      "notes": ["نمایش یادداشت‌های انتشار و بهبود روند به‌روزرسانی برنامه"]
    }
  ],
  "channels": [
    {
      "id": "direct",
      "version": "4.0.0",
      "versionCode": 11,
      "updateUrl": "/download/student.apk"
    }
  ]
}
```

* `releases` تاریخچه یادداشت‌های **کاربرمحور و فارسی** هر نسخه است؛ آن را از changelog فنی توسعه جدا نگه دارید. یادداشت‌های نسخه‌های بعد از نسخه نصب‌شده تا نسخه هدف با هم نمایش داده می‌شوند.
* `minimumVersion` و `minimumVersionCode` باید به یک نسخه ثبت‌شده اشاره کنند. این حد را فقط برای مشکل بحرانی، امنیتی یا ناسازگاری لازم بالا ببرید؛ برابر بودنش با جدیدترین نسخه الزامی نیست.
* `channels` فقط مسیرهایی را فهرست می‌کند که واقعاً همان نسخه و همان `versionCode` را ارائه می‌کنند. شناسه‌های پشتیبانی‌شده `cafeBazaar`، `myket` و `direct` هستند. برنامه جدیدترین `versionCode` موجود را انتخاب می‌کند و فقط کانال‌های دارای همان نسخه هدف را نشان می‌دهد.
* مسیر نسبی `updateUrl` نسبت به مبدأ فایل v2 resolve می‌شود؛ URL مطلق HTTPS نیز قابل استفاده است. لینک کانال را فقط پس از انتشار همان APK در آن کانال فعال کنید.
* برای نسخه‌های تاریخی که یادداشت واقعی ندارند، `notes` خالی است؛ یادداشت نسخه‌های بعدی را پیش از انتشار وارد کنید. چون لینک انتشار واقعی بازار و مایکت در اختیار نیست، نمونه فعلی فقط کانال مستقیم را فعال می‌کند.

### ۵.۳. قرارداد نسخه اندروید

در `frontend/apps/student/android/app/build.gradle`:

* `versionName` نام خوانای نسخه است و برای نمایش و انتخاب یادداشت‌ها استفاده می‌شود.
* `versionName` را برای هر انتشار کاربرمحور تغییر دهید تا یادداشت‌ها و نسخه نمایشی آن انتشار قابل تشخیص باشند.
* `versionCode` عدد صحیح اندروید برای ترتیب و امکان نصب ارتقایی است. برای هر انتشار جدید آن را افزایش دهید و در تمام کانال‌ها از همان package name، کلید امضا و artifact استفاده کنید تا ارتقای بین کانال‌ها سازگار بماند.
* نگارش‌های تاریخی ممکن است `versionName` متفاوتی با یک `versionCode` داشته باشند؛ تاریخچه نمونه منعکس‌کننده همین نگاشت است. از این پس هر انتشار جدید باید `versionCode` بالاتری داشته باشد.

### ۵.۴. رفتار رابط کاربری

* **به‌روزرسانی اجباری:** اگر `installedVersionCode < minimumVersionCode` باشد، صفحه تمام‌صفحه RTL نمایش داده می‌شود. یادداشت‌ها به‌صورت پیش‌فرض بسته‌اند و دکمه به مرحله انتخاب کانال‌های دارای نسخه هدف می‌رود. این صفحه قابل رد کردن نیست؛ کلید بازگشت اندروید مطابق رفتار فعلی برنامه آن را دور نمی‌زند.
* **به‌روزرسانی اختیاری:** اعلان شناور غیرمسدودکننده باقی می‌ماند. با بازکردن جزئیات، یک bottom sheet یادداشت‌ها و سپس انتخاب کانال را در همان پنل نشان می‌دهد.
* **خطای شبکه یا manifest نامعتبر:** اعلان خطا و تلاش مجدد نمایش داده می‌شود و استفاده از برنامه را مسدود نمی‌کند.

### ۵.۵. کش و مرز امنیتی

برای هر دو فایل نسخه، در Nginx مبدأ دانش‌آموز هدر جلوگیری از کش طولانی‌مدت تنظیم کنید:

```nginx
location = /app-version.json {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
    add_header Pragma "no-cache";
    expires 0;
}

location = /app-version-v2.json {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
    add_header Pragma "no-cache";
    expires 0;
}
```

بررسی نسخه سمت کلاینت ابزار هماهنگی انتشار و تجربه کاربری است، نه مرز امنیتی. برای مسدودسازی امنیتی نسخه‌های قدیمی، کنترل سمت بک‌اند لازم است.

## ۶. ناوبری و کلید بازگشت فیزیکی اندروید (Hardware Back Button)

با ادغام پلاگین `@capacitor/app` و ماژول `mobileNavigation`:
1. در صورتی که باتم‌شیت (مانند جزئیات چالش، ارسال مدارک یا جزئیات پاداش) باز باشد، اولین فشردن کلید بازگشت، باتم‌شیت را می‌بندد.
2. در صفحات فرعی برنامه (مانند `/challenges`, `/rewards`, `/notifications`)، فشردن کلید بازگشت به صفحه قبلی بازمی‌گردد.
3. در صفحه اصلی (داشبورد `/` یا صفحه ورود `/login`)، فشردن کلید بازگشت برنامه را به آرامی می‌بندد و از افتادن در حلقه ناوبری جلوگیری می‌کند.

## ۷. مراحل بیلد و تولید خروجی نهایی (APK / AAB) در Android Studio

پس از اجرای `npm --prefix frontend run cap:build:student`:

1. پروژه را در **Android Studio** باز کنید (`npm --prefix frontend run cap:open:student`).
2. صبر کنید تا Gradle فرآیند ایندکس و سینک را به پایان برساند.
3. **تست روی شبیه‌ساز یا دستگاه متصل:**
   * دستگاه فیزیکی یا امولاتور مورد نظر را از نوار ابزار بالا انتخاب کنید.
   * دکمه **Run 'app'** (آیکون مثلث سبز یا کلید میانبر `Shift + F10`) را بزنید.
4. **تولید خروجی دستی برای انتشار (Signed APK / AAB):**
   * از منوی بالا به مسیر **Build > Generate Signed Bundle / APK...** بروید.
   * گزینه **Android App Bundle** (برای گوگل پلی) یا **APK** (برای کافه‌بازار، مایکت یا نصب مستقیم) را انتخاب کنید.
   * فایل کلید امضا (Keystore) خود را انتخاب کرده یا با زدن **Create new...** یک کلید امضای معتبر جدید بسازید. (کلید امضا و کلمه عبور را در جای امن نگهداری کنید و هرگز در گیت کامیت نکنید).
   * نوع بیلد (Build Variant) را روی **release** قرار دهید.
   * هر دو گزینه **V1 (Jar Signature)** و **V2 (Full APK Signature)** را تیک بزنید.
   * دکمه **Finish** را بزنید تا خروجی نهایی تولید شود. فایل‌های کامپایل‌شده در مسیر `android/app/release/` قرار خواهند گرفت.

## Real-time and FCM push notifications

The Android app registers its FCM token after the student authenticates and receives native system alerts while backgrounded or closed. Firebase project setup, `google-services.json`, backend service-account configuration, permissions, logout behavior, and verification steps are documented in [Real-time and Android Push Notifications](../../../docs/notifications-realtime.md).
